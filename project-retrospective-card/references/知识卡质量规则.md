# 知识卡质量规则（v1.4.0）

## 定位与长度
知识卡服务于快速了解和复用项目经验，完整证据保留在项目内容总文档。先列出3—5个核心管理问题，再沿“问题—方法—成果”主线写卡，禁止按每份文件扩写一段。全文建议2000—3500个非空白字符，硬上限6500（包含YAML、表格和引用）。资料不足时按已知信息写短稿，不凑字、不编造。

保留原始9个YAML字段、联系人代码块、5个二级标题及顺序。可在阅读笔记新增项目周期等小项，不增设二级标题。

| 栏目 | 内容与约束 |
|---|---|
| YAML | 年度只填四位项目年份，跨年周期放阅读笔记；不推断行业代码，缺证据写待核实；tags为3—8个有依据标签，不强凑；aliases只填资料明确的名称；资料来源为总文档及最多4份主要资料的列表 |
| 联系人 | 仅必要姓名、部门岗位、工作联系方式、项目职责；代码块总长度≤220非空白字符；不填证书、入职经历、人才测评分数、性格/推动力评价 |
| 项目背景 | 标签一行；叙述100—200字（剔除标签和引用），只讲发展阶段、管理矛盾和启动缘由；栏目总长度≤260非空白字符；资料不足可少于100字但须明确“资料不足” |
| 核心问题 | 3—5条客户实际管理问题，≤600非空白字符；不得把盘点发现、具体人员分档或项目组产能难点当作客户初始诉求；不足3项如实简写 |
| 最终成果 | 3—5条“核心问题｜解决方案｜最终成果｜状态与依据”，≤1400字符；只选关键诊断发现辅助解释，不展开全套名单、分数、建议清单；技术建议书、访谈提纲等过程文件写入方法，不单列最终成果 |
| 其他备注 | ≤1400字符；挑战最多3项，最佳实践/可复制方案各最多2项；缺依据可省略可选项；不重复背景、核心问题和交付清单 |
| 阅读笔记 | ≤2000字符；精简来源映射、阅读边界、待核实及人工确认清单；不复制全部资料清单，不额外扩写商务延伸方向；完整清单已在总文档 |

正文以项目事实和可复用认识为主。未知状态在成果表简短标记，完整边界集中在阅读笔记；同一风险/待核实事项不在每个栏目反复展开。不要把知识卡写成对Agent规则的解释或免责声明集合。

## 客户问题、项目发现和实施挑战分开
- 客户问题：立项前需解决什么实际管理矛盾，优先取明确需求或经确认的项目目标。
- 项目发现：开展诊断后识别的事实和判断，放成果中的关键发现，不能回填成已知的初始诉求。
- 实施挑战：数据缺失、范围调整、沟通协调、产能等，放其他备注。
- 不得从“存在一个交付文件”反推“客户必然存在一个对应问题”。例如访谈提纲不证明客户诉求混乱，技术建议书不证明双方未形成共识。

## 证据强度与成果状态
优先级：明确交付/验收/审批/实施记录 > 正式成果正文 > 访谈纪要/工作记录 > 已有复盘/个人体会 > Agent分析。目录名“客户提交版”、文件日期、措辞“拟/计划”只提供线索，不能单独证明已提交、已确认、已实施。

| 状态 | 所需依据 |
|---|---|
| 已形成 | 存在实质性成果文件内容，只能说明形成了什么 |
| 已提交 | 明确提交/发送/汇报记录；若仅项目组复盘称已提交，标为“据项目组记录，待核实” |
| 已确认 | 客户确认、批准、验收等明确记录 |
| 已实施 | 实际执行记录，方案中写“实施步骤”不够 |
| 已产生效果 | 实施及跟踪记录；仅结果变化也不能自动认定由项目导致 |
| 拟议/待核实 | 仅建议、方案设计，或证据不足；允许保留但不升级事实状态 |

所有关键结论、状态与关键数字均定位到具体来源和页/段/工作表单元格，转换无页码时使用总文档行号。原始摘录写入临时证据表，卡内只保留简短依据。找不到证据就降低表述或删除，不用“待核实”给明显缺依据的强结论兜底。

## 数据口径与矛盾处理
- 文件统计只复制run_project返回的statistics_sentence，不能手工改写总数、分项或转换数量。总文档保存完整文件索引，来源映射只列卡内引用项。
- 区分：发现文件数、转换完成数、Agent自报阅读范围、图像等语义覆盖；转换成功不代表全文已读或图中信息已理解。禁止笼统写“未读取项：无”。
- 人数、分组、分母、时间、范围先统一，再做加总、比例与比较；不能一边写“待核实”一边继续用有冲突的值下确定结论。
- 无法统一时，核心正文不输出依赖该争议数值的比例/相关性/排序；阅读笔记并列两种口径及其出处、影响和需确认内容。
- 自行加总与计算比例必须在临时calculations中登记terms/total或numerator/denominator/percent。直接引用原文数字也要核对口径与证据。程序只验证已登记的计算，不自动证明所有数字正确。

## 来源与阅读覆盖
总文档每个来源有`## S0001`等稳定标题及完整路径。卡内可用Obsidian链接：`[[总文档文件名#S0001|S0001]]`，附页码/工作表/段落；只有转换行号时写`S0001，总文档L120—135`。不引用临时文件。
阅读笔记的映射表格式固定：`编号｜完整相对路径｜定位`；不使用省略号。每个S编号均须存在且被映射。完整材料、全部来源和详细结果保留在总文档，不为了压缩知识卡删除总文档正文。

## 经验提炼及信息取舍
经验用“场景—实际措施—已知结果—可借鉴原则—适用边界”表达，区分实际做法、事后反思和Agent建议。没有效果证据则明确效果未验证，不包装为最佳实践。
不把“主动越级”“直接套用模型”等个人做法写成普遍准则；提炼为明确角色、协调权限、事项升级和适用条件等可操作原则。
默认以群体特征介绍人才盘点结果；删除员工姓名+测评分数/负面判断及不必要个人履历。联系人必要业务信息可以保留。私有原资料仍留在本地总文档，不因知识卡精简而删改源文件。

## 临时质量复核记录
run_project解析合并后返回review_file（工作区内card_review.json）。Agent完整读取总文档、写卡后填入该文件；不作为第三份交付物，--finish通过后自动清理。

```json
{
  "read_ranges": [[1, 120]],
  "claims": [
    {
      "source_id": "S0001",
      "locator": "总文档L20—25",
      "excerpt": "对应来源中可以精确找到的原始摘录",
      "card_phrase": "这项证据对应的卡内原句",
      "status": "已提交",
      "status_basis": "明确提交记录及定位；证据不足应改用已形成/待核实"
    }
  ],
  "calculations": [
    {"kind":"sum", "label":"样本加总", "terms":[3,7,3], "total":13, "card_phrase":"卡内对应原句"},
    {"kind":"percentage", "label":"比例", "numerator":3, "denominator":13, "percent":23.1, "tolerance":0.1, "card_phrase":"卡内对应原句"}
  ],
  "semantic_review": {
    "scope_separation":true,
    "status_support":true,
    "conflicts_constrain_claims":true,
    "minimal_personal_data":true,
    "reuse_boundaries":true,
    "numbers_reviewed":true
  }
}
```

以上120行、摘录、数字和状态均为结构示例，必须换成本项目真实数据。阅读范围为1-based闭区间，覆盖总文档所有实际行；这是Agent自报覆盖，代码只能检查范围连续性，不能证明认知上的充分理解。claims覆盖关键背景、问题、发现、成果及其状态，可多条绑定同一来源；不得用一条无关摘录替代全卡证据。无自行计算时calculations可为[]。

Agent填完后自动运行`run_project.py --finish workspace`。有错误则保留工作区，修正卡片/复核表后重试；不绕过检查，不清理证据后再补写。强判断提示需结合证据修订。代码无法自动判定状态依据是否充分、逻辑因果、个人信息必要性和全部数字的语义正确性，最终仍须提醒项目组确认。
